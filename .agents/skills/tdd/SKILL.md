# TDD

テストの追加、バグ修正、機能実装ではこの方針に従う。

## 保証

テストが言うのは、そのテストが見た振る舞いが、与えた入力の範囲で壊れていないこと。正しさの証明にはしない。

緑は、テストが通っている状態である。言及した振る舞いが今も成り立つことであり、壊したくない性質には、それを観測するテストを付ける。テストが無い性質は、緑でも守られていない。

## 作業の範囲

変えてよいのは次だけである。

- 観測する振る舞いのテスト
- 今の計算結果を返す関数への移動
- その振る舞いを直す実装

テストスクリプトが何もしないときだけ、そのスクリプトをテストランナーの起動に変えてよい。新しい設定ファイルは、既存の設定で実行できないときだけ足す。依存とロックファイルは足さない。依頼が名前を挙げていない表示は足さない。

## 手順

新しい振る舞いを固定するとき:

1. 起きてほしい場合を、実装を混ぜずに一覧にする。
2. 一つだけ、準備・呼び出し・断言のある失敗するテストにする。
3. そのテストと、それまでのテストを通す。途中で思いついた場合は一覧へ戻す。
4. 緑のあとで、必要な分だけ形を整える。
5. 一覧が空になるまで 2 に戻る。実装が変わらない例は足さない。

緑にする方法は次のいずれか。

- 実装が見えているならそのまま書く。
- 見えていなければいったん定数で通し、その定数とテストの期待値との重複を消して一般化する。
- 一般化が見えないときだけ、定数では通れない二つ目の例を足す。

断言を消して緑にしない。実行結果を期待値へ貼らない。期待値を書く前に、正確な値か、指定した丸めかを一つ決める。

既存の不具合は、今の誤った結果で失敗するテストから入る。計算が描画の枠の中にあるときは、そのテストより前に、作業の範囲の「今の計算結果を返す関数への移動」を行う。この移動は振る舞いの変更ではない。新しい機能は、利用者から見た一つの場合を先に置き、その内側をこの手順で満たす。

UI や DOM 検出を変更するときは、その変更を直接検証する単体・結合テスト（`pnpm test`）を追加または更新し、実行する。既存テストが変更後の振る舞いを直接検証している場合は、そのテストを実行する。

## 一つの振る舞い

単位はクラスやメソッドではなく、一つの振る舞い。結果を説明する断言は複数あってよい。テスト名はその場合を一つの文で言う。

決定的で、入力が値で出力が値のものは実物を使い、出力を見る。プロセスの外へ出る命令で、自分たちが境界を持っているものだけ、その契約を最小のダブルで見る。内部の関数が呼ばれたかは見ない。自分たちのものではないライブラリの呼び出しは置き換えない。

準備に必要な値はそのテストの中で読めるようにする。実行順、時計、乱数、ネットワーク、待ち時間、実行環境のロケールに依存させない。失敗したときは、名前と断言からどの振る舞いが壊れたか分かるようにする。

## 書かないもの

価値は「退行を捕まえる」「整理に耐える」「速い」「読める」の積である。どれかがゼロなら置かない。

次は書かない。

- 動機を一文で言えないテスト
- ダブルを満足させるためのテスト
- 振る舞いを保った整理だけで赤くなるテスト
- カバレッジのためのテスト
- 自明な委譲と、枠へ値を渡すだけの部分

テストコードの重複は、意図が読めなくなる抽出より残す。
