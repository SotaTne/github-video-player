# pr

pull request は、人が一度に読める一つの理由である。差分が変化で、本文が理由である。作成か分割を頼まれたときだけ出す。文面だけを頼まれたときは、出さずに文面を返す。

## 単位

一つの pull request は、タイトルが一つの文になる範囲である。コミットが分かれていても、理由は一つである。

- タイトルに「と」が要るときは分ける。コミットが積んであるときは、履歴を書き換えない。各 pull request の差分はそのコミットだけにし、後の pull request のベースは直前のコミットにする。
- 一つのコミットに複数の理由があるときは、頼まれない限りそのコミットを割らない。割らないときは、共通の一つの目的をタイトルにし、本文で各理由を一文ずつ書く。
- その変更を固定するテストと、その変更で偽になる文書は同じ pull request に入れる。ユーザーが分けると指定したときは、その指定に従う。
- ビルドと、その変更が触れていないテストが通る状態で出す。ユーザーが失敗するテストだけの pull request を頼んだときは、本文に、失敗することと、期待が仕様であることを書く。
- ユーザーが除いた変更は入れない。秘密と認証情報は入れない。

## 文章

直近の pull request のタイトルの言語に合わせる。無ければ、直近のマージ以外のコミットの言語に合わせる。日本語なら日本語、英語なら英語である。

タイトルは命令形の一文で、それだけで何をしたか分かる。日本語は辞書形にし、句点で終えない。コミットがタ形でも、タイトルはタ形にしない。英語は大文字で始め、ピリオドで終えない。目安は 50 文字、上限は 72 文字である。`feat:` などの接頭辞は、直近の pull request がそれを使っているときだけ付ける。

本文は散文である。定型の見出しとチェックリストは書かない。

- 差分に無い理由を書く。解決している問題と、このやり方を選んだ理由である。理由は、差分、履歴、ユーザーの言葉にあるものだけである。そこに無い動機は書かない。履歴にある変更前の状態は一文で書いてよい。入れなかった変更があるときは、その一文を書く。どちらも無いときは本文を書かない。
- この pull request に入れなかった変更があるときだけ、それを一文で書く。
- 差分から読めない設計の決定があるときだけ、それを一文で書く。
- 差分を見ても確認方法が分からないときだけ、確認を一文で書く。
- 差分の復唱とファイル一覧は書かない。
- 72 文字で折る。段落のあいだは空行にする。

ベースは、既存の pull request の向き先である。無ければ、そのブランチが分岐したブランチである。

レビューで差分が変わったら、タイトルと本文を今の差分に合わせる。

## 手順

1. 状態、対象の差分、コミット、既存の pull request のタイトルを見る。
2. 自分で差分を読む。
3. 上の単位に分ける。
4. 出すときは、タイトルと本文をリポジトリの外のファイルに書き、その範囲を push して pull request を作る。リモートが無いときと、文面だけを頼まれたときは、リポジトリにファイルを作らない。タイトル、本文、対象コミットを応答で返し、URL は作らない。
5. 出した範囲と、入れなかった変更を確認する。

## 例

一つの理由:

```
GitHub Actionsで品質検査のCIを実行する

初期構成にはフォーマッタやリンタが無く、ブラウザ実行コードに Node.js
の型が混入する問題があった。

oxfmt と oxlint を導入し、ブラウザ用の tsconfig.json からテスト用の
tsconfig.test.json を分離して CI で検査を実行する。
動画プレイヤーの実装は、この pull request には入れていない。
```

コミットを割らず、理由が二つあるとき:

```
差分画面の折りたたみと翻訳表示の崩れを直す

差分を閉じたときは本文要素が消えるが、外側要素へフォールバックして
ヘッダーごと非表示にしていた。
同じコミットにある翻訳後の残存テキストは、テキストノードの除去と
翻訳抑止属性で防ぐようにした。
```
